# Mobile / VPN performance optimization — 2026-11-07

Implementation, production builds, and validation are complete. The frontend build
has been updated. The release backend is ready; the existing port-7682 process was
not restarted because it owns live shell sessions. Backend changes therefore take
effect on the next normal service restart. No claim below describes an in-place
upgrade of that old running process.

## Changes

1. Status refresh requests only Git repository metadata, avoiding full tracked and
   untracked file reads, diff parsing, and unused diff transfer. Full diff requests
   and terminal-target validation remain available unchanged.
2. Static assets reuse bounded, router-local raw/gzip caches (16 MiB, 32 entries,
   individual files up to 4 MiB). Metadata/ETag revalidation detects rebuilds. The
   entry page is prewarmed before listening. API/SSE/WS traffic bypasses this cache.
3. Two-pass Terser compression reduces cold-load bytes while keeping all features
   inside one HTML file, with no additional requests, CDN or HTTPS dependency.
4. Mobile mounts only its visible sidebar. A separate memoized terminal-mode
   context prevents unrelated session revisions from rerendering the terminal.
   Breakpoint subscriptions support both modern and older Safari APIs.
5. WebGL activation runs after opening the terminal, so GPU failures are caught
   and cleanly fall back to the DOM renderer.
6. Ordinary PTY connections now close their descriptors and reap their shell on
   disconnect. Cancellable, nonblocking pumps avoid both injected EOF and leaked
   descriptors. An event-driven cancellation socket adds no periodic idle polling.
   Thread joins and child waits run off Tokio workers. Queued input is bounded to
   64 × 8 KiB chunks and preserves bytes across partial writes/backpressure.
7. Tmux disconnect still detaches only clients owned by that connection. It does
   not inject newline/Ctrl-D into shared sessions. TTY ownership is cleared before
   the OS can reuse its name during a fast reconnect.

## Measurements

| Measurement | Before | Optimized |
|---|---:|---:|
| Metadata response with a 10,000-line untracked fixture | >170 KB full diff | <1 KB, identical repository fields |
| Same-body localhost HTTP response, warm median | 30.72 ms | 0.60 ms |
| First HTTP request after readiness | 31.53 ms | 1.22 ms |
| Actual HTML gzip bytes in weak-network matrix | 241,653 | 234,155 |
| P2 cold document, median of 3 runs | 8,514 ms | 8,265 ms |
| Browser reload transfer | 300 bytes / actual 304 | 300 bytes / actual 304 |
| After opening/closing 3 ordinary shells: FD growth | +6 | 0 |
| After opening/closing 3 ordinary shells: thread growth | +3 | 0 |
| Unreclaimed shells in that experiment | 3 | 0 |

P2 applies **400 ±150 ms in each direction and 32 KB/s** using toxiproxy. Three
fixed rounds were retained. Ctrl-C completed in every sample: median-of-run p50
999 → 982 ms, p95 1,032 → 1,050 ms. Buffered-outage recovery completed in every run,
with medians 1,140 → 1,242 ms. These small, mixed timing differences under jitter
are not evidence of an interaction speedup or statistical equivalence; the
measurable improvement here is transfer size, with no observed functional failure
or timeout. No extra rounds were added to improve the result.

The PTY resource result was also reproduced with zsh: 10 FDs / 68 threads before
and after, and no retained test shells. Each of three 4 MiB raw-transfer samples
per version matched its SHA-256 exactly. Local sample ranges were 164–283 MiB/s
before and 240–297 MiB/s after (medians 259 and 248); this noisy microbenchmark is
not a throughput-speedup claim. Both are far above the target VPN bandwidth.

The final Safari compatibility follow-up adds a few bytes: final served HTML gzip
is **234,183 bytes**. Exact frontend/backend SHA-256 values are recorded in
[final-artifacts.json](2026-11-07/final-artifacts.json).
